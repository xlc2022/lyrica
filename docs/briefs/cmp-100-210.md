# Brief: int8 paths for the CMP 100-210

Owner: the Agent loop thread. Tests: the CMP 100-210 thread, on danube.

## Why

The CMP 100-210 (PCI ID `10de:1df4`) is a Volta card (sm_70) whose firmware
cuts its FP16 tensor cores to about 6% of a V100's. Everything else runs at
full speed: FP32, plain FP16, memory, and int8 dot products (dp4a, 56 TOPS).
Measured on danube with Z-Image Turbo at 1024², 8 steps:

| Path | Per step |
|---|---|
| ComfyUI, FP16 | 8.35 s |
| ComfyUI, FP8 weights, FP32 compute | 6.3 s |
| stable-diffusion.cpp, default build | 8.2 s |
| stable-diffusion.cpp, int8 (`GGML_CUDA_FORCE_MMQ`), flash attention off | 3.0 s |

ggml sends large quantized matrix multiplies on Volta to cuBLAS in FP16 on
the tensor cores, and its flash attention uses them too. Forcing its int8
kernels and turning flash attention off avoids the throttled unit. The card
then runs at its 250 W limit.

The owner's rule: a fix for this card is applied only when the host detects
it by its PCI ID. A problem that would affect every GPU is a bug, fixed
normally (as #457 did for recipe sizing).

## What

1. **llama.cpp (first PR).** `install.sh` looks for a GPU with PCI ID
   `10de:1df4`. If it finds one, it adds `compose.cmp.yaml`, which builds
   llama.cpp from source, at the tag of the stock image, with
   `GGML_CUDA_FORCE_MMQ=ON`, for the compute capabilities of the host's own
   GPUs, in place of the stock CUDA image. Forcing MMQ changes nothing on
   Turing or newer cards: ggml picks MMQ for them anyway
   (`ggml_cuda_should_use_mmq` returns before the flag). Flash attention
   stays llama.cpp's own choice: on danube, with Qwen3-8B Q4_K_M and a
   6.5k-token prompt, the stock image read about 320 tokens/s and wrote 68;
   this build read 836 and wrote 69 with flash attention on, but 768 and
   55 with it off.
2. **Images (second PR).** On a host with a CMP, recipes run on the CMP
   (`COMFY_GPU`) go to stable-diffusion.cpp's `sd-server` instead of
   ComfyUI. It is built from a pinned commit for sm_70 with
   `GGML_CUDA_FORCE_MMQ=ON`, converts weights to Q8_0 as it loads them
   (`--type q8_0`), and leaves flash attention off. sd-server takes a model
   as start-up arguments, so a small supervisor starts it for the recipe
   host-api names in a file, as gate.py does for ComfyUI. It covers create
   for the templates sd.cpp supports (Z-Image, FLUX, SDXL, Qwen-Image),
   without LoRAs. ComfyUI isn't started on that host (its PyTorch has no
   sm_70 kernels anyway), so edit, upscale and other recipes fail saying
   why. Like ComfyUI, it saves nothing, logs nothing and has no route out.
3. **Faster prompts (third PR).** On sm_70, llama.cpp's flash attention
   uses the throttled tensor cores (WMMA/MMA) for long prompts. A small
   patch (`llamacpp/volta-fa-tile.patch`) adds `GGML_CUDA_VOLTA_FA_TILE`,
   which `compose.cmp.yaml` sets, so it uses the tile kernel throughout;
   other cards' kernels don't change. host-api also gives a model placed
   on the CMP `ubatch-size = 2048` (llama.cpp's own is 512). On danube
   with the same model and prompt: the tile kernel read 961 tokens/s
   instead of 836, 979 with the bigger steps, writing unchanged at about
   69. FP32 cuBLAS and draft models gained nothing; n-gram speculation is
   unproven.

## Out of scope

Ready-made Q8_0 files (they would halve the cold load), edit and upscale
through sd.cpp, and any change to clocks, power limits or firmware.

## Checks

- The host's tests cover the image routing and the recipe list on a host
  using sd.cpp.
- On danube: install, then a text model reading a long prompt, and a
  Z-Image Turbo create, each compared with the numbers above. Danube is
  shared, so the host stays paused, with its GPU free, outside the test.

## Handoff (2026-10-22, from the danube thread)

Written so anyone, Lyrica included, can pick this up from the repo alone.

### The rule behind every change

The card's FP16 *tensor cores* are throttled; FP32, plain FP16, memory
bandwidth and int8 dot products (dp4a) are not. Every fix moves work off
the tensor cores and onto int8 or FP32. A fix applies only when the host
sees PCI ID `10de:1df4` (`install.sh`, `nvidia-smi
--query-gpu=pci.device_id` = `0x1DF410DE`); nvidia-smi names the card
"Tesla V100-PCIE-12GB", so never detect it by name.

### What is built (#466, #471, #472)

- **llama.cpp** (`host/llamacpp/Dockerfile`, `host/compose.cmp.yaml`):
  the stock image's tag (`b11459`, commit pinned) built from source with
  `-DGGML_CUDA_FORCE_MMQ=ON` and `CMAKE_CUDA_ARCHITECTURES` from
  `CUDA_ARCHS` (`70-real` on danube, written to `.env` by `install.sh`).
  Flash attention is left to llama.cpp (on is faster), with one patch,
  `host/llamacpp/volta-fa-tile.patch`, applied after the clone: inside the
  `volta_mma_available(cc)` branch of `ggml_cuda_get_best_fattn_kernel`
  (`ggml/src/ggml-cuda/fattn.cu`), `GGML_CUDA_VOLTA_FA_TILE` (set in
  `compose.cmp.yaml`) makes it return the tile kernel instead of the
  tensor-core one for large batches. host-api writes `ubatch-size = 2048`
  for a model placed on a CMP (`cmp` in `host/src/backends.ts`).
- **Prebuilt images** (`host/prebuilt.sh`, `.github/workflows/cmp-images.yml`):
  CI builds both images and `install.sh` pulls them by digest, building
  here only when it can't (docs/briefs/cmp-prebuilt-images.md).
- **Images** (`host/sdcpp/`, `host/compose.sdcpp.yaml`,
  `host/src/sdcpp.ts`): stable-diffusion.cpp's `sd-server` at a pinned
  commit, same `FORCE_MMQ` build, started by `gate.sh` with `--type q8_0`
  (weights become Q8_0 as they load) and `--flash-attn off`. It runs as
  uid 10001, the owner of the models folder's `lyrica/`, because that
  folder can be mode 700 (it is on danube). ComfyUI isn't started.

### Measured on danube (Qwen3-8B Q4_K_M, 6.5k-token prompt; Z-Image Turbo 1024², 8 steps)

| Setup | Prompt tok/s | Gen tok/s |
|---|---|---|
| Stock llama.cpp image | ~320 | 68 |
| CMP build, flash attention on (in main) | 836 | 69 |
| CMP build, flash attention off | 768 | 55 |
| + `-b 2048 -ub 2048` | 890 | 69 |
| + flash-attention tile patch, ub 512 | 961 | 69 |
| + tile patch and ub 2048 (#472) | 979 | 69 |

- Z-Image Turbo through sd-server: ~28 s per image warm (~3.0 s/step),
  ~143 s extra for the cold load (Q8_0 conversion over a PCIe Gen1 x1
  link). Power peaks near the 250 W limit.
- `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` (a runtime switch already in
  llama.cpp): no change with flash attention on, since nothing in that
  model goes to cuBLAS (769 to 809 tok/s with it off).
- Draft model (Qwen3-0.6B Q8_0): no gain (77 tok/s with or without);
  longer drafts are slower. `--spec-type ngram-mod` was faster only on a
  repeated prompt: unproven.

### Speech

- Dictation (Whisper on vLLM v0.30.0) can't run: vLLM's PyTorch has no
  sm_70 kernels ("no kernel image is available"), so a CMP never runs
  vLLM, and a dictation model with no other GPU says so.
- **Dictation through whisper.cpp works** (tested outside the host, not
  yet in it; docs/briefs/cmp-whisper.md is the plan). Build: whisper.cpp
  `v1.9.5` (commit `d1be6fde`), same flags as llama.cpp
  (`-DGGML_CUDA=ON -DGGML_CUDA_FORCE_MMQ=ON
  -DCMAKE_CUDA_ARCHITECTURES=70-real -DGGML_NATIVE=OFF`) plus
  `-DBUILD_SHARED_LIBS=OFF`, targets `whisper-server` and `whisper-cli`
  (39 MB together, needing only the CUDA 12.8 runtime). Run it with a
  working directory other than `/app` when borrowing the llama.cpp image,
  or ggml loads that image's own `libggml-cuda.so`. Models: the
  `ggerganov/whisper.cpp` repository (revision `5359861c`),
  `ggml-large-v3-turbo*.bin`. Times with the model loaded, flash
  attention on (off is 5-15% slower):

  | Model | 36 s English | 180 s English | 16 s Mandarin | Load |
  |---|---|---|---|---|
  | fp16 | 2.3 s (15x) | 10.2 s (18x) | 1.3 s | 8.7 s |
  | q8_0 | 1.7 s (21x) | 6.1 s (29x) | 1.0 s | 4.8 s |
  | q5_0 | 1.7 s (21x) | 6.4 s (28x) | 1.0 s | 3.2 s |

  Transcripts were accurate in both languages. Use q8_0, kept loaded
  (about 1 GB).
- Voice (Kokoro, speech server): ONNX Runtime 1.23.2 with cuDNN 9.27
  fails on sm_70 (`CUDNN_STATUS_EXECUTION_FAILED_CUDART` in the LSTM);
  cuDNN probably dropped Volta (unverified). So a CMP never runs the
  speech server, and on a host whose GPUs are all CMPs it runs on the CPU:
  danube's i5-4590 reads at 2.8x real time, all in one part. The server
  runs as 10001, so it reads a mode-700 `lyrica/`.

### How to test on danube

- It is shared: its other user comes first. Keep the host paused and
  the GPU at about 9 MiB except during a test; check with `nvidia-smi`.
  sudo needs the operator.
- Docker: the session's shell may lack the docker group; use
  `sg docker -c "..."`. The host's checkout is
  the one on danube (see the CMP thread).
- The dashboard API answers on `http://127.0.0.1:7236` at the machine
  with no Origin header: `/host/v1/resume`, `/pause`, `/downloads`,
  `/models/load`, `/models/unload`, `/models/settings`,
  `/images/create`. `/v1` is refused there; reach a model server through
  host-api's container (`docker exec -i lyrica-host-host-api-1 node
  --input-type=module -` with a script on stdin, fetching
  `http://llamacpp:8080/completion`).
- Benchmarking a build without the host: run its image as
  `--user 10001:10001 --gpus all`, mount the models folder read-only,
  publish on `127.0.0.1`, and remove the container afterwards.
- Building on danube is slow (4-core i5: llama.cpp 25 min, sd-server
  18 min). Images built on Lunasa reached danube at only ~2 MB/s; the
  prebuilt images from GHCR (#472) replace both. For a quick test, build
  only the binaries on Lunasa (`docker build --output type=local`), as
  for whisper.cpp: tens of MB instead of a 2 GB image.
- The whisper.cpp test files on danube (binaries, models, and synthetic
  English and Mandarin recordings made with Kokoro) are in a
  `whisper-test` folder beside the host's checkout.
